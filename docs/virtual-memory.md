# Виртуальная память Malospal OS

Ядро больше не остаётся на таблицах страниц загрузчика: оно создаёт свои
четырёхуровневые таблицы x86-64 и переключает CR3. Пока используется одно
адресное пространство ядра и страницы по 4 КиБ.

## Проверка

Из корня репозитория в PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\kernel\build.ps1 virtual
```

Тест проверяет инициализацию, права страниц, создание и удаление отображений,
смену прав, повторное отображение того же адреса на другую физическую страницу,
возврат пустых таблиц и отказы при нехватке памяти. В конце ожидаются
`MALOSPAL_VMM_TEST_OK` и `PASS`.

UEFI-вариант:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\kernel\build.ps1 virtual -Memory 256 -Uefi
```

Намеренно нарушить защиту памяти:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\kernel\build.ps1 fault -Exception write-protect
powershell -NoProfile -ExecutionPolicy Bypass -File .\kernel\build.ps1 fault -Exception stack-overflow
```

В вариантах `fault` сообщение `[panic]` ожидаемо. Тест сверяет номер ошибки,
код, адрес обращения и регистры, затем закрывает свой QEMU.
Обычный образ не содержит намеренных ошибок.

| Значение `-Exception` | Проверяемое нарушение | Ожидаемый результат |
| --- | --- | --- |
| `write-protect` | Запись после смены RW на R | Page Fault, код 3 |
| `no-execute` | Переход на страницу данных с NX | Page Fault, код `0x11` |
| `stack-guard` | Чтение нижней защитной страницы | Page Fault, код 0 |
| `unmapped` | Чтение адреса после удаления отображения | Page Fault, код 0 |
| `text-write` | Запись в код ядра | Page Fault, код 3 |
| `stack-overflow` | `push` за нижнюю границу основного стека | Double Fault на отдельном стеке IST |

Образы и журналы: `kernel/build/virtual/` и `kernel/build/fault-*/`.
Полная команда `check` включает 30 локальных групп и 63 запуска QEMU:
4 проверки загрузки, 22 аварийных сценария, по 3 проверки PMM, VMM, таймера и консоли,
6 проверок экрана и резервных режимов, 5 проверок PS/2-клавиатуры,
4 проверки Змейки, 4 проверки слот-машины и 6 USB-сценариев.
Конфигурации VMM: BIOS с 32/128 МиБ, UEFI с 256 МиБ.

## Отображения и права

| Область | Права |
| --- | --- |
| Код ядра `.text` | Чтение и исполнение, без записи |
| Константы `.rodata` | Только чтение, исполнение запрещено |
| Данные, BSS, стеки, запросы загрузчика | Чтение и запись, исполнение запрещено |
| Прямое отображение доступной RAM (HHDM) | Чтение и запись, исполнение запрещено |
| Выбранный framebuffer в HHDM | RW/NX, WC через PAT5 или UC; не обычная RAM |
| Окно MMIO устройств с `0xffffc00100000000` | RW/NX/UC, отдельно от окна RAM |
| Восемь защитных страниц стеков | Не отображены |
| Нижняя половина адресного пространства | Не отображена |

Все страницы доступны только привилегированному коду (supervisor). Включены
CR0.WP и IA32_EFER.NXE, поэтому ограничения записи действуют и для кода ядра,
а страницы данных нельзя исполнять. Поддержка NX обязательна; пятиуровневый
режим LA57 и включённый PCID на входе пока не поддерживаются.

HHDM сохраняет смещение, полученное от Limine. В новых таблицах отображаются
целые страницы `USABLE`, кроме физической страницы 0, и отдельно страницы
проверенного framebuffer. Память ядра, загрузчика, ACPI и остальных устройств
туда не добавляется. Поэтому код
ядра и защитные страницы не получают второго, доступного для записи адреса.
Данные ответов Limine заранее скопированы; после переключения нельзя обращаться
к старым указателям ответов. Память загрузчика пока не возвращается в PMM.

Framebuffer сохраняет прежний виртуальный адрес, поэтому экран доступен до
и после смены CR3, включая диагностику исключений. Диапазон целиком должен лежать
в регионе `FRAMEBUFFER`, не пересекаться с RAM, ядром или динамическим окном.
Используется WC из PAT5, заданного протоколом Limine; резервный режим UC использует
PCD/PWT и PAT3. Перед переключением выполняется `sfence`. Отображения устройства
нельзя менять или создавать для них алиасы через динамический интерфейс VMM.
[Подробности framebuffer](screen.md).

Для xHCI добавлены `vmm_map_mmio_page()` и `vmm_unmap_mmio_page()`. Окно 16 МиБ
принимает страницы MMIO из RESERVED или дыр карты памяти, исключая RAM, ядро,
framebuffer и данные прошивки. Обычный `vmm_protect_page()` не может убрать UC.
PAT3 проверяется независимо от выбранного режима framebuffer. После удаления
MMIO-страниц пустые таблицы возвращаются в PMM; это проверяется в VMM-тестах.

Каждый из четырёх стеков имеет недоступную страницу до и после рабочей области.
Выход за нижний край основного стека мешает доставке page fault, поэтому
диагностику выполняет double fault на собственном IST-стеке.
Это обнаружение обращения к соседней странице, а не защита от произвольного
скачка указателя стека через неё. Восстановления после ошибки пока нет.

## Контракт интерфейса

Объявления: `kernel/include/malospal/vmm.h`. Реализация x86-64:
`kernel/src/arch/x86_64/paging.c`.

- `vmm_init(boot)` вызывается после PMM с той же проверенной копией `boot_info`.
  Успешное переключение возможно один раз. При отказе до переключения
  временные таблицы освобождаются, прежний CR3 сохраняется.
- `vmm_map_page(virtual, physical, flags)` создаёт отображение одной страницы.
  Уже занятый виртуальный адрес не заменяется. При нехватке памяти новые
  промежуточные таблицы откатываются.
- `vmm_protect_page(virtual, flags)` меняет права существующего отображения.
- `vmm_unmap_page(virtual, &physical)` удаляет отображение и возвращает адрес
  физической страницы. Саму страницу данных не освобождает, пустые таблицы освобождает.
- `vmm_query(virtual, &mapping)` возвращает физический адрес с учётом смещения
  внутри страницы и права. Для отсутствующего отображения возвращает `false`.
- `vmm_root_physical()` и `vmm_table_pages()` возвращают корень и число страниц таблиц.

Изменяемые отображения ограничены окном размером 2 ГиБ:
`0xffffc00000000000` ... `0xffffc0007fffffff`. Начальные отображения ядра
и HHDM нельзя изменить через эти функции. Адреса map/unmap/protect должны быть
выровнены на 4096 байт. Флаги изменения: 0 (R/NX) или `VMM_WRITE` (RW/NX).
`VMM_EXECUTE` возвращается запросом для кода ядра, но не принимается
динамическими операциями. Физический адрес должен принадлежать отображённой RAM.

Вызывающий код обязан владеть страницей, полученной из PMM, и удалить все её
динамические отображения перед возвратом в PMM. VMM не ведёт владельцев и
счётчиков ссылок, не проверяет право вызывающего кода на конкретную страницу.
Это внутренний интерфейс доверенного ядра, а не граница безопасности процессов.
RO в динамическом окне не запрещает запись через сохраняющийся RW-адрес HHDM.

Изменения активных таблиц сопровождаются `invlpg`. Перед первым переключением
сбрасываются и глобальные трансляции загрузчика. Правила кэширования адресов
описаны в [Intel SDM, раздел 5.10](https://cdrdv2-public.intel.com/868137/325462-089-sdm-vol-1-2abcd-3abcd-4.pdf).

## Проверки и ограничения

Проверяется реальный CR3, включение WP/NX, права секций, все восемь защитных
страниц, отсутствие прямых алиасов кода и guards, доступ к данным через два
адреса, границы PT/PD, очистка TLB и возврат количества свободных страниц
к исходному после удаления временных отображений.
Также проверяются каждая страница framebuffer, RW/NX, биты кэширования,
запрет динамических алиасов/изменений и отказ PMM освобождать видеопамять.

Для проверки начального отказа тест оставляет от нуля до шести свободных
страниц, пытается построить таблицы и проверяет неизменность CR3 и счётчиков.
После успешной инициализации отдельно проверяется нехватка памяти на каждом
из трёх уровней новой ветви. Затем отображение создаётся успешно, чтобы
подтвердить работоспособность после отказов.

Пока нет пользовательских адресных пространств, больших страниц, ленивого
выделения, copy-on-write, переключения процессов, поддержки SMP и TLB shootdown.
PMM/VMM вызываются только одним CPU с отключёнными маскируемыми прерываниями,
не из обработчиков NMI/исключений. После включения таймера вызывающий код
использует `arch_irq_save()` / `arch_irq_restore()` вокруг операций с памятью.
Обработчик таймера не обращается к PMM/VMM. Общий интерфейс MMIO за пределами
выбранного framebuffer и освобождение памяти
загрузчика потребуют отдельной реализации. Реальное оборудование не проверено.
