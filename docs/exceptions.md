# Ошибки процессора в Malospal OS

Когда процессор обнаруживает ошибку, он передаёт управление обработчику
из таблицы IDT. Теперь эту таблицу и обработчики устанавливает ядро Malospal OS.
Оно выводит причину и состояние процессора через COM1 и на доступный framebuffer,
после чего останавливается. Экран использует общий диагностический вывод;
повторный вход в занятый экранный драйвер пропускается без ожидания блокировки.
Продолжение работы после ошибки пока не реализовано.

## Попробовать

Из корня репозитория в PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\kernel\build.ps1 fault -Exception page-fault
```

Команда создаёт отдельный тестовый образ и запускает его в QEMU. Ядро намеренно
читает отсутствующую страницу по адресу `0x0000400000000000`. Сообщение
`[panic] CPU exception` здесь ожидаемо: тест проверяет его поля, закрывает свой
экземпляр эмулятора и выводит `PASS`, если диагностика правильная.
Это ошибка гостевого ядра внутри QEMU, а не ядра Windows.

Проверка аварийного стека при UEFI-загрузке:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\kernel\build.ps1 fault -Exception double-fault -Uefi
```

В этом тесте основной стек намеренно направляется в отсутствующую страницу.
При доставке исключения возникает double fault. Процессор переключается на
выделенный стек IST, и обработчик всё равно может напечатать диагностику.
Тест требует строку `handler_stack=double-fault-IST`, полученную проверкой
фактического адреса кадра, а не только номера исключения.

Также доступны `divide`, `invalid-opcode` и `general-protection`.
Для проверки новых таблиц страниц добавлены `write-protect`, `no-execute`,
`stack-guard`, `unmapped`, `text-write` и `stack-overflow`.
Последний сценарий выполняет запись ниже нижнего края настоящего стека ядра
и проверяет диагностику double fault на отдельном стеке.
[Подробности защиты памяти](virtual-memory.md).
Для полного набора проверок загрузки, исключений и памяти:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\kernel\build.ps1 check
```

Обычный запуск `run-kernel.cmd` не вызывает искусственных ошибок. Его образ
остаётся в `kernel/build/normal/`; аварийные варианты и журналы располагаются
отдельно в `kernel/build/fault-*/`.

## Читать журнал

| Поле | Значение |
| --- | --- |
| `vector`, `name` | Номер и название исключения; например, 14 и Page Fault |
| `error` | Код с дополнительными сведениями; смысл зависит от исключения |
| `rip` | Сохранённый адрес инструкции; для тестируемых ошибок, кроме double fault, это инструкция, вызвавшая сбой |
| `rsp` | Сохранённый указатель прерванного стека |
| `cs`, `ss`, `rflags` | Сегменты и флаги процессора |
| `cr2` | Адрес обращения для page fault; для других исключений не обязательно связан с текущим сбоем |
| `rax` ... `r15` | Снимок регистров общего назначения |
| `handler_stack` | Проверка размещения кадра на стеке double fault; `other` само по себе не означает ошибку |

Для исключений без аппаратного кода ошибки ассемблер добавляет ноль, чтобы
у C-обработчика был единый формат кадра. В тестах с `fault` QEMU завершается
через специальное тестовое устройство; в обычной сборке ядро после диагностики
остаётся остановленным до выключения эмулятора.

## Устройство

- `kernel/src/arch/x86_64/exceptions.c`: собственные GDT/TSS/IDT, настройка IST и вывод диагностики.
- `kernel/src/arch/x86_64/stacks.S`: четыре стека и защитные страницы по краям.
- `kernel/src/arch/x86_64/exceptions.S`: загрузка GDT, 256 входных обработчиков, сохранение регистров и возврат из IRQ.
- `kernel/src/arch/x86_64/interrupts.c`: разделение аппаратных IRQ и фатальных исключений.
- `kernel/src/arch/x86_64/exceptions.h`: общий формат кадра для C и ассемблера с проверками размеров.
- `kernel/tests/fault.S`: инструкции одиннадцати аварийных сценариев.
- `kernel/tests/vmm_fault.c`: подготовка отображений для тестов защиты памяти.
- `kernel/tools/build.py`: отдельные образы, запуск QEMU и проверка полей журнала.

GDT описывает сегменты и TSS. TSS содержит указатели стеков, а IDT определяет
входной обработчик и при необходимости индекс аварийного стека IST.
Основной стек занимает 64 КиБ, отдельные стеки double fault, NMI и machine check
занимают по 16 КиБ. По краям каждого стека есть недоступные страницы по 4 КиБ.
Проверка повреждённого стека выполнена для double fault;
NMI и machine check пока не вызывались тестами.

После настройки PIC/PIT обычное ядро разрешает внешние прерывания. Векторы
32..47 обслуживаются как IRQ, обработчик возвращается через `iretq`.
Исключения 0..31 и остальные неожиданные векторы остаются фатальными.
Аварийные тесты по-прежнему выполняются до включения IRQ.
Поддерживается один процессор и только код ядра; пользовательский режим и
восстановление после исключений остаются будущими этапами.
[Прерывания и таймер](interrupts-timer.md).

Формат таблиц, 64-битного кадра и правила доставки исключений сверены с
[Intel Software Developer's Manual](https://cdrdv2-public.intel.com/868137/325462-089-sdm-vol-1-2abcd-3abcd-4.pdf)
и [AMD64 Architecture Programmer's Manual, Volume 2](https://docs.amd.com/v/u/en-US/24593_3.44_APM_Vol2).
